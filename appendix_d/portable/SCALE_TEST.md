# 商品数とPC負荷の検証（pilot.5）

確認済みの商品は全件対象です。旧版の倉庫ごと20商品・確認CSVの200行制限をPortable経路から外しました。履歴不足などの予測不可条件は引き続き表示します。対象商品を黙って切り捨てません。

## 現場PCでの手順

1. 業務用とは別フォルダーへZIPを展開し、初期設定で「IT動作確認」を選びます。人工データを業務用Dataへ混ぜないでください。
2. 起動後、`ScaleSamples/SYNTHETIC-100-products.zip` をアップロードします。
3. 数量は箱、神戸の拠点コードはKOBE、拠点名は神戸倉庫、基準時刻は16:00として確認します。人工データは2026年1月1日〜2月4日の35日分です。
4. JAN対応と出荷0日の扱いを確認し、担当者・理由を入力します。「PCの負荷を調整・検証する」で100商品ずつを選び、「確認して予測を開始」を押します。
5. 結果が100商品×14日＝1,400行になったことを確認します。一括ダウンロード、商品選択ダウンロード、1件の修正・フィードバックも試してください。
6. 「PCの処理時間・メモリ使用量」を開き、時間・最大メモリ・成功状態を記録します。タスクマネージャーでもPC全体の使用率と他アプリの操作感を確認してください。
7. 500商品、1,000商品を順に試します。結果はそれぞれ7,000行、14,000行です。重い場合は一度終了して他アプリを閉じ、小分け設定25商品で比較します。

同じデータの完了結果は再利用されます。100/25/一括の速度を公平に比較するときは、毎回ZIPを別の空フォルダーへ展開し、新規Dataで同じ条件を使ってください。各アプリは順に終了し、同時起動を避けます。既存の業務Dataを消す必要はありません。

IT担当者へ渡す記録：アプリ版、商品・倉庫数、履歴日数、分割設定、完了時間、タスクマネージャーのメモリ/CPU、操作の遅さ、`Data/State/Performance` のJSON、失敗した場合の `Data/Logs`。測定JSONは端末内に保存し、自動送信しません。

## 大量の場合の対策と現在の限界

- 予備予測は25/100/500商品ずつ、または全件一括で処理できます。総商品数の制限ではありません。完了した小分け結果を保存し、同じ入力・同じ確認条件で再実行すると再利用します。途中バッチの中断はそのバッチから計算し直します。
- 正式予測Workerは同一サーバー内で1件ずつ実行します。結果画面は30行ずつ表示し、全件/商品選択ダウンロードを使えます。
- 分割は予備予測部分です。在庫取込、履歴整形、正式予測、結果JSONは全体をメモリに持つ箇所が残っています。25商品にすれば必ず全体のメモリが減る、無制限の件数がどのPCでも動く、とは保証しません。
- ZIPの100MiB、展開合計1GiB、5,000ファイルの安全制約は維持しています。商品数による切り捨てではなく、超過時はエラーにします。
- メモリ不足が続く場合はIT担当者が倉庫または商品群ごとに入力ZIPを分け、各対象の**全履歴と在庫を同じ範囲**で含めて順に実行します。日時だけで分割すると履歴不足になるため避けます。分割結果は別実行として保管し、未処理商品・重複商品を照合してください。分割ZIPの自動生成や複数実行結果の自動統合はまだありません。
- 正式予測自体が限界になった場合の次工程は、正式予測を商品単位で永続キュー化し、共通データ版・予測基準日を維持して結合する方式です。現場の測定結果で優先度を判断します。

数値はサーバープロセス全体の250ms間隔サンプリングです。ブラウザー・他アプリを含むPC全体の必要メモリではなく、瞬間的なピークは見逃す場合があります。各段階は重なるため、時間を合計して総時間にしないでください。人工データは負荷検証用で、予測精度の評価には使えません。
