## 2. 学習方式

初期の固定方式は前2年のTRAINでfit_parametersを1回実行し、3年目の各起点までの利用可能な実績でrefresh_contextを実行する。
パラメータ、TRAIN残差分布をTESTで再推定しない。
毎日起点への変更は可能。月次再学習E-2/E-3は`MONTHLY_EXPANDING`として、各月最初の予定originまで学習窓を拡大する。
`run_fixed_provider`は登録済みの固定学習Provider、`run_monthly_provider`は月次拡大学習を共通実行する。旧名`run_fixed_baseline`は互換wrapperとして維持する。AutoETSは各学習締切でモデル構造・平滑化パラメータ・初期状態を確定し、次の再学習まで各起点の履歴へ`forward`で適用する。MLForecast Ridgeは各学習締切でlag・曜日特徴から系列別係数を確定し、次の再学習まで各起点の履歴へ再帰適用する。

## 3. 入力と営業日

基本365日、うるう年366日。dsはJST業務日を表すtimezoneなし00:00。
unique_idは空でない文字列。yは非負実数、未観測はNaN。確定した出荷ゼロだけ0とする。
日付NaT、日中時刻、同一商品・同日重複、bool・無限大・未処理負数量は拒否する。
返品・取消、規格変更、JAN名寄せ、取扱期間判断、原本の訂正版選択は上流で処理する。
ForecastDatasetの配列はtupleへコピーし、ProviderConfig.paramsはimmutable化する。
Registryの登録ID・生成ProviderのIDは一致必須。baselineの未知paramsは拒否する。

## 4. 実績の利用可能時刻

締切は起点翌日00:00 JST。ds<=起点を満たす履歴だけを使う。
- ASSUMED：実績が締切までに利用可能だったという仮定。結果に仮定を表示する。
- OBSERVED：timezone付きavailable_atを確認し、締切を超えた行は残してy=NaNとする。

datasetとrunnerのavailability_modeは一致必須。異なる方式は同一比較へ混ぜない。
入力は一商品・一日一行の版確定済みデータ。過去訂正履歴の自動復元はこのrunnerの機能ではない。
OBSERVEDのhistorical residual時点再現は未実装のため、baseline区間予測はblocking error。点予測は利用できる。

## 5. 将来変数

known_future_columnsは列名の許可リストであり、それだけで「当時既知」を証明しない。
v2.9 runnerは生データの最終確定列を直接将来変数に結合しない。

### 5.1 固定カレンダー

次の予約名のみ、対象日から内部で決定的に生成する。
- calendar_dayofweek：月曜0～日曜6
- calendar_month：1～12
- calendar_day：1～31
- calendar_is_month_start：月初1、それ以外0

外部データで上書きできない。祝日や販促など変更され得る情報はこの一覧に含めない。

### 5.2 変更される変数

runnerのfeature_versions引数に独立した版テーブルを渡す。

| 列 | 契約 |
|---|---|
| unique_id | 商品・拠点系列の文字列 |
| ds | 値が適用される対象日、timezoneなし00:00 |
| feature | known_future_columnsに指定する変数名 |
| value | 非欠損の有限実数 |
| known_at | その値が確定・変更された実時刻、timezone付き |

各起点・対象日・系列・変数ごとに、known_at<=起点翌日00:00 JSTのうち最も新しい版を選ぶ。
同じ時刻の同一キー版重複は拒否する。既知版がない場合は契約違反として停止し、未来の確定値や0で埋めない。
履歴へ渡す変数も当該起点の締切で同様に選択する。初期TRAINはTRAIN末尾起点の締切を使用する。
ASSUMEDであっても変更される将来変数のknown_at要件を省略しない。

dataset_snapshot_idは実績と将来変数の版テーブルを含む凍結データ全体を識別する。版テーブルや列定義を変更したらsnapshotを更新する。
この識別子の発行と永続保存は上流の責務。任意IDの使い回しで再現性を主張しない。
旧v2.8のraw列受け渡しは互換ではない。値の通過試験をknown_at付き版テーブルへ移行し、未来変更が過去結果へ影響しない試験を追加した。

## 6. 出力・baseline

出力列：unique_id / origin_date / target_date / horizon / forecast_kind / quantile / yhat_raw / yhat。
POINTはquantile=NULL。QUANTILE=0.5は本当の中央値。QUANTILEのqは0<q<1、小数6桁以内。
yhat=max(0,yhat_raw)。POINTと中央値の大小は仮定せず、QUANTILE間だけ順序検証する。
予測対象日は起点+horizon、horizonは整数、モデル・dataset上限と要求範囲を守る。

| 方式 | 規則 | 最小有効観測日数 |
|---|---|---|
| seasonal_naive_7 | 起点以前の直近同曜日。欠測なら4候補まで遡る | 7 |
| moving_average_28 | 起点を末尾とする28暦日。NaNを分母から除外 | 28 |
| same_weekday_mean_4 | 起点以前の同曜日4候補の有効値平均 | 28 |
| seasonal_naive_364 | 364日単位で起点以前の同曜日を参照 | 364 |

全候補欠測なら予測不能。最小履歴不足も全予定の母数には残す。
区間要求時はTRAIN内で同じ欠損規則の残差を作り、fit時にキャッシュする。
分位出力は点予測+経験残差分位。残差中央値を差し引かない。
残差10件未満は区間未提供。要求分位の全件出力か0件のみ許し、部分出力は契約違反。
区間は統計的被覆を保証しない。初期デモは点予測のみ。

## 7. 全予定照合と例外

予測前にbuild_planで全予定を固定する。保存前にreconcile_predictionsを必ず通す。
空出力・系列欠落・日付欠落はFAILED、区間未提供はUNAVAILABLE。欠落を成功扱いしない。
厳密な完全出力検査にはvalidate_predict_frameのexpected_targetsを渡す。

runnerの学習・起点処理中のProviderErrorはerrorsへ記録する。
その他のExceptionはUNCLASSIFIED_ERRORとし、exception_type、message、traceback、origin_date、retryable=Falseを記録する。
起点単位の障害は次の起点へ継続し、学習失敗は全予定FAILEDで返す。
ContractViolationErrorは欠測へ変換せず送出する。入力検証・Provider生成などの事前設定エラーも実行前に解決する。

## 8. 精度比較の3集合

mode/horizonの選択は先に固定する。以下の計算母集団を混同しない。

| 指標 | 母集団 | 比較相手追加時の挙動 |
|---|---|---|
| own_metrics | 自run自身の予定のうちtruthと予測が揃うキー | 他runの追加・失敗・起点間隔によって変化しない |
| common_metrics | 全runの共通予定のうちtruthと全予測が揃うキー | 全runを比較するため縮むことがある |
| official_common_metrics | 完全runだけを選定後、そのrunどうしの共通予定でtruthが揃うキー | 不完全runの追加によって縮まない |

run_*は選択したmode/horizon内の全予定・成功・失敗・成功率。truth欠損で予測失敗を消さない。
own_planned_count / own_truth_eligible_count / own_truth_missing_count / own_success_countを単独指標に併記する。
shared_* / truth_*は全run共通集合の件数として旧意味を維持する。own_*と取り違えない。

official_runsは自runの全予定で予測失敗0、かつ自runに評価可能なtruthがあるrun。
評価レジストリ経由の正式集合は、これに加えて固定条件のProvider適合試験を全項目通過したrunだけを含む。適合未通過でもown/common指標と失敗件数は保存・表示する。
不完全runは表示から消さずown_metricsとrun_success_rateを併記する。own_metricsを同一集合のランキングとして並べない。
正式対象の確定後に、official_runsだけから共通予定を作り直す。不完全runの予定は参照しない。
異なる起点間隔も同一の商品・起点・対象日・horizonへ揃える。通期modeでは運用profileの一致を要求する。

ranking_ready：全run厳格比較が成立。
official_evaluation_ready：正式集合に評価対象があり、完全runが1つ以上。
official_ranking_ready：正式集合に評価対象があり、完全runが2つ以上。
1つだけなら単独評価であり、比較で優勝したという表示をしない。
いずれもモデル適合試験・本番採用判断の代替ではない。

## 9. 集合IDと指標

comparison_set_id：全run比較用。scope、truth版、mode/horizon、run集合、共通予定・共通成功キー。
official_comparison_set_id：正式比較専用。policy版、scope、truth版、mode/horizon、正式run集合、正式予定・truth有効キー。
正式対象を変えたら正式IDも変わる。不完全runだけの追加なら正式IDは維持する。
実運用ではrun名に一意のrun IDを使用し、同じIDで予測や学習条件を書き換えない。

WAPEとBias rateは百分率でwape_pct / bias_rate_pct。biasは誤差総量、MAEは平均絶対誤差、RMSEは二乗平均平方根、under/overは数量。
実績0の日を除外しない。WAPE・Bias rateの分母0はNULL、評価0件なら全指標NULL。
正式比較の予定数・truth有効数・truth欠損数も返す。

## 10. 通期と累計

通期は成功結果を見る前にprimary_planで対象日ごとの最新予定起点を選ぶ。失敗時に古い成功予測へ戻さない。
重複horizonがあっても最新起点で1日1件にできれば被覆成立。異なる運用profileの通期比較は禁止。
累計は起点ごとの1..window日が全件揃う場合のみ計算。年末打切り、truth欠損、予測失敗を区分する。
重複する10/15日窓の誤差を年間不足量として合算しない。

## 11. 本文全体仕様との共通Contract（Phase 1A / 1B）

Phase 1Aで次の型・時点・識別契約を追加した。詳細と移行例は[Phase1A_契約と移行.md](Phase1A_契約と移行.md)。
- ProviderConfig.preprocessing_version: 必須・非空文字列・immutable。
- RunContext.cutoff_at / availability_mode: 必須。for_originでfit/各起点に個別contextを派生する。
- RunContext.failure_sink: 型付きFailureRecordの記録先。省略可。DB依存は持たない。
- ModelRef: train_start_date、weights_id、preprocessing_version、parameter_fingerprint、availability_mode。
- ContextRef.cutoff_at: 呼出contextの締切を保存し、predict前にmodel/origin/cutoffを照合する。

weights_id=Noneは外部の学習済み重み非該当。前処理識別はProviderConfigから引き継ぐ。
fingerprintは学習条件と依存環境の決定論的SHA-256。学習時刻・UUID・起点履歴を含めない。
sink障害は元の失敗recordを保持するFailureSinkErrorで停止する。既存errorsの分類・形式は維持する。
Phase 1BでModelRef/ContextRefの版付きJSON、ローカル保存・復元、artifact checksumを追加した。
保存先とProvider固有Codecは差し替え可能。保存contextは正確なモデルartifactとrun/起点/締切へ結び付く。
別プロセスの復元後も再fitせず同じ予測を再現する。詳細は[Phase1B_保存と復元.md](Phase1B_保存と復元.md)。

実行中のstateはプロセス内オブジェクトだが、baselineは明示的な保存/復元APIを利用できる。
Workerジョブ再開・二重出力防止・強制タイムアウト・分散実行・再試行制御は後続実装。

Phase 1Cでrun/origin/expectation/value/failureとmodel/context artifact参照を扱うRunStore境界を追加した。SQLite参照実装は起点単位transaction、condition fingerprint照合、attempt fencing、完了起点の再利用、retryable障害の最大3 attempt、キャンセル後の次起点抑止を実装する。本番PostgreSQL、複数Workerのlease期限・heartbeat、強制timeoutは後続実装とする。

Phase 1DでPostgreSQL migrationとRunStoreを追加した。複数WorkerはSKIP LOCKEDで起点をclaimし、worker ID・lease token・期限・heartbeatで所有権を検証する。期限切れは新attemptとして回収し、旧Workerの結果を拒否する。起点timeout後の遅延結果は保存しない。OSレベルのresource隔離とrun全体timeoutは後続実装とする。

Phase 1Eでrun作成・状態取得・キャンセル・同条件再開のBearer認証付きAPIを追加した。HTTP request内では学習・予測を行わず、独立Worker processが信頼されたデプロイ済みOriginExecutorを呼ぶ。run APIから任意moduleやコードを指定できない。role別権限とUIはPhase 1Q、Phase 1Pで追加した。外部IdPとTLS終端は後続実装とする。
データsnapshotの永続発行、訂正履歴・feature版の保管、適合試験記録も上流・DBの責務。

Phase 1Fでdataset snapshotと実験定義の版付き不変catalogをSQLite/PostgreSQLへ追加した。runは保存済み実験だけから作り、起点と予定はサーバー側で生成する。組込baseline Workerはsnapshot checksumを検証し、Phase 1BのModelRef/ContextRefを別プロセスで復元する。動的な将来特徴量はURI・checksum・known_at付き版を必須とする。データuploadと訂正承認は後続実装とする。

Phase 1Gでサーバー管理領域からの原本取込jobと独立Workerを追加した。原本byte列はSHA-256で不変保存し、同一内容を重複、同一論理pathの異なる内容を訂正版候補として記録する。ZIP traversal・容量・同名衝突を拒否し、厳密に判定できない文字コードはファイル単位で隔離する。CSV列変換、訂正版の採用承認、JAN名寄せ、日次確定は後続実装とする。

Phase 1Hで内容アドレス方式の列mapping、出荷行正規化job、訂正版採用履歴、数量照合、品質APIを追加した。原JAN・原本行を維持し、日付・数量・単位・行区分・available_atの不正を理由付きで隔離する。負数量や返品を0補正・自動相殺しない。JAN名寄せ、取扱期間、予定ファイル完全性、日次状態確定は後続実装とする。

Phase 1Iで採用中原本の成功済み正規化行から決定論的なJAN名寄せ候補を生成するjobと独立Workerを追加した。名称一致だけでは自動統合せず、SAME_PRODUCT、DIFFERENT_PRODUCT、SUCCESSOR、UNRESOLVEDを承認者・理由・mapping version付きで記録する。canonical product、両端包含のJAN有効期間、商品×center取扱期間をSQLite/PostgreSQLへ保存し、同じ版の期間競合をtransactionで防止する。予定ファイル完全性と日次状態確定は後続実装とする。

Phase 1Jで内容アドレス方式の予定ファイル定義、center×日付の完全性、6種類の日次状態、時点付き休業日を追加した。採用中原本の成功済みnormalization、JAN版、取扱期間版、休業版、選定系列、期間、availability modeを日次buildへ凍結する。独立Workerは予定0件・未到着・部分到着・隔離行・0確定条件を区別し、全暦日の決定的CSVとchecksumを生成して、上流provenance付きdataset snapshotをcatalogへ自動登録する。休業日に実出荷があれば実績を維持して矛盾を記録し、buildの`as_of`より後に利用可能になった実績・休業情報を使わない。詳細は[Phase1J_予定完全性と日次状態.md](Phase1J_予定完全性と日次状態.md)。

Phase 1Kで成功済み日次buildを対象とする3〜5品目の受入case、10項目の技術判定、決定的なJSON/Markdown品質レポート、版付き業務判断を追加した。匿名データは`DRY_RUN`に固定し、実データ受入として承認できない。詳細は[Phase1K_少数実品目受入.md](Phase1K_少数実品目受入.md)。

Phase 1Lで成功済み日次buildを母集団とする重要品目候補算出jobを追加した。数量、数量構成比、変動係数、出荷0率は利用可能値だけから算出し、欠損率は取扱対象値を分母にする。JAN変更、業務指定、対象centerと分類tagを候補へ保存する。担当者は候補から初期3〜5品目または拡大20〜50品目を理由付きで選び、不変な`selection_version`として確定する。詳細は[Phase1L_重要品目候補と選定版.md](Phase1L_重要品目候補と選定版.md)。

Phase 1MでStatsForecast AutoETSを2つ目のOSS Providerとして追加した。日次週周期、明示パラメータ、因果的前方補完、実観測28日以上、POINT予測を初期適合条件とする。学習済み状態はpickleを使わず厳密なJSONへ保存し、署名でcontext更新・予測・復元時のパラメータ不変を検査する。baselineとAutoETSは同じ固定学習runner、snapshot検証、予定表、失敗台帳、評価処理を使う。詳細は[Phase1M_StatsForecast_AutoETS.md](Phase1M_StatsForecast_AutoETS.md)。

Phase 1ZでMLForecast Ridgeを3つ目の予測Providerとして追加した。lag 1・7・14・28日と曜日、alpha 1.0、実観測かつ補完後56日以上、POINT予測を初期適合条件とする。学習済み状態は特徴名、係数、切片だけをpickleなしのJSONへ保存し、署名でcontext更新・予測・復元時の不変を検査する。3 Providerは同じ固定学習runner、snapshot検証、予定表、失敗台帳、評価処理を使う。詳細は[Phase1Z_MLForecast_Ridge.md](Phase1Z_MLForecast_Ridge.md)。

Phase 2AでApache-2.0のTimesFM 2.5 200Mを4つ目の予測Providerとして追加した。固定revision・file size・SHA-256を検証したローカルsafetensorsだけをzero-shot推論へ使い、実行時ダウンロードを禁止する。最大512日の因果的補完済みcontext、horizon 1〜400、POINT予測を初期適合条件とする。重みとPyTorch objectはartifactへ保存せず、CPU PyTorchは専用Workerだけへ導入する。TimesFM 3.0重みは非商用ライセンスのため対象外とする。詳細は[Phase2A_TimesFM_2p5.md](Phase2A_TimesFM_2p5.md)。

Phase 2BでTimesFM専用Workerの起動前検査と運用計測を追加した。固定checkpoint検証と実効read-only、モデル初期化、warm-up、反復推論のwall/CPU time、process peak RSS、cgroup CPU・memory上限を別項目として記録し、8項目の技術判定を内容アドレス方式のJSONへ保存する。既定の`cpu-timesfm`はCPU 2、memory 4 GiB、人工3系列、context 512日、horizon 15である。benchmark serviceはnetworkを持たず、checkpointをread-onlyで参照する。詳細は[Phase2B TimesFM運用計測](Phase2B_TimesFM運用計測.md)。

Phase 2Cで実データ受入プリフライトを追加した。取込入力、原本archive、snapshot、受入report、プリフライトreportの5 rootについて、存在、読取、symlink、相互重複、application境界、実効read/writeを検査する。PostgreSQL 17への接続、Phase 1X〜1Kで必要な23 relation、SELECT・INSERT・UPDATE権限を合わせた10項目を判定し、path、DSN、database/user名、原本名を含まない内容アドレス方式JSONへ保存する。`READY_FOR_DATA`は実データ投入準備だけを示す。詳細は[Phase2C 実データ受入プリフライト](Phase2C_実データ受入プリフライト.md)。

Phase 2DでPostgreSQL隔離リカバリ訓練を追加した。custom archiveを内部生成の一時DBへ復元し、backup前後の元DB安定性、archive検証、schema・sequence・全table行のstreaming SHA-256一致、一時DB削除を検査する。6判定と所要時間を内容アドレス方式JSONへ保存し、DSN、DB/user名、path、relation名、行値は保存しない。詳細は[Phase2D PostgreSQL隔離リカバリ訓練](Phase2D_PostgreSQL隔離リカバリ訓練.md)。

Phase 2Eで全7管理画面にOIDC Authorization Code + PKCE S256を追加した。stateと5分期限、redirect URI完全一致を検証し、APIが固定token endpointでcodeを交換する。access tokenはURL、cookie、local/session storageへ保存せずmodule memoryだけで使用する。詳細は[OIDC PKCEログイン](Phase2E_OIDC_PKCEログイン.md)。

Phase 2Fで外部IdP接続プリフライトを追加した。issuerから導出したDiscoveryと設定済みJWKSをsystem trust store・hostname検証付きHTTPS、redirect禁止、timeout・応答サイズ上限付きで取得する。issuer・3 endpointの完全一致、Authorization Code、PKCE S256、許可署名方式、互換公開鍵と重複のない`kid`を含む14項目を検査し、全件合格だけを`READY_FOR_IDP_LOGIN`とする。URL、host名、公開鍵値、例外本文を保存せず、設定URLのSHA-256と判定を内容アドレス方式JSONへ保存する。詳細は[外部IdP接続プリフライト](Phase2F_外部IdP接続プリフライト.md)。

Phase 1NでProvider適合試験と比較結果の不変レジストリを追加した。適合記録はProvider/model/library/adapter設定、実行環境、試験suite、7項目の結果・証跡を完全識別し、掲載可否をサーバーで導出する。比較APIは保存済みrunとchecksum検証済みsnapshotだけから既存評価式を実行し、比較条件、2種類の集合ID、scope hash、run別件数・指標をSQLite/PostgreSQLへ保存する。詳細は[Phase1N_評価レジストリ.md](Phase1N_評価レジストリ.md)。

Phase 1Oで保存済み比較を決定的なUTF-8 BOM付きCSVとして内容アドレス方式で発行する機能を追加した。baseline改善率は全run共通集合のWAPEで算出し、0除算を空欄にする。CSVは件数、own/common/official指標、単位、集合・snapshot・selection・Provider・適合記録の識別子を含み、取得時にもchecksumを再検証する。採用判断は正式ランキング、異なる採用・fallback run、実データ受入のPASSEDと最新APPROVED、日次build、対象品目・centerを照合し、版付きで上書きせず保存する。詳細は[Phase1O_比較レポートと採用判断.md](Phase1O_比較レポートと採用判断.md)。

Phase 1PでFastAPIと同一originの比較・受入・採用管理画面を追加した。Bearer tokenはブラウザーのメモリ内だけで扱い、比較一覧、run別指標・系譜、受入caseの業務判断、比較CSVの発行・取得、採用・却下を既存の不変台帳へ接続する。採用候補はadoption context APIがchecksum検証済みsnapshotと台帳から返し、保存時にはPhase 1Oのserviceが全条件を再検証する。詳細は[Phase1P_比較受入採用管理画面.md](Phase1P_比較受入採用管理画面.md)。

Phase 1Qでsubjectとroleを持つ複数Bearer credential、READ・ANALYZE・APPROVE・EXPORTのendpoint別permissionを追加した。監査用担当者項目は互換入力を残しつつ認証subjectで上書きする。productionは複数credentialとHost allowlistを必須とし、API・管理画面への平文HTTPを拒否して共通security headerを付与する。詳細は[Phase1Q_認証認可とセキュリティ.md](Phase1Q_認証認可とセキュリティ.md)。

Phase 1Rで外部IdPのJWT access tokenをJWKS公開鍵、許可algorithm、issuer、audience、時刻claim、role mappingで検証するOIDC modeを追加した。credential fileはatomic置換を検知し、不正更新時はfail closedとする。APIは構造化監査log、公開liveness・readiness、READ権限付きmetricsを提供する。本番ComposeはCaddyだけを外部公開し、API・PostgreSQL・全Workerを分離する。PostgreSQL 17 custom archiveはSHA-256 manifestを検証し、復元先DB名の明示一致後に単一transactionで復元する。詳細は[Phase1R_本番運用基盤.md](Phase1R_本番運用基盤.md)。

Phase 1Sで`FIXED`と`MONTHLY_EXPANDING`をExperimentへ固定し、同期runnerと分散Workerで同じ月次学習締切を使用する。月次runはreference比較に分離する。採用済みchampionとfallbackからLifecycle計画を作り、期限到来cycle、WAPE改善率・失敗率gate、APPROVERによるrevision付き昇格、過去championへのrollback、実績利用可能前のtrial予測記録、30日以上の`FUTURE_TRIAL`評価を追記型台帳へ保存する。詳細は[Phase1S_継続学習とモデル切替.md](Phase1S_継続学習とモデル切替.md)。

Phase 1TでFastAPIと同一originの`/ui/lifecycle`を追加した。READ利用者は計画、現在champion、全event、cycle、trial記録を参照できる。ANALYZE利用者はscheduler、cycle処理、予測事前記録、APPROVE利用者は計画作成、昇格、rollback、trial評価を操作する。ブラウザーは操作後に台帳を再読込し、最終状態と監査主体はサーバーが確定する。詳細は[Phase1T_Lifecycle運用画面.md](Phase1T_Lifecycle運用画面.md)。

Phase 1UでFastAPIと同一originの`/ui/readiness`を追加した。READ利用者は商品×centerの取扱期間履歴、日次buildの上流版、予定ファイル完全性、6種類の日次状態、欠測理由を参照できる。APPROVE利用者は取扱期間を登録できる。日次行の状態・商品・center検索とページング、状態・理由集計はDBで行い、ブラウザーは保存後にサーバー台帳を再読込する。詳細は[Phase1U_取扱期間と欠測判定画面.md](Phase1U_取扱期間と欠測判定画面.md)。

Phase 1VでFastAPIと同一originの`/ui/selection`を追加した。READ利用者は候補job、数量・構成比・変動係数・出荷0率・欠損率、分類、対象center、選定可否、確定済み選定版を参照できる。ANALYZE利用者は候補jobを登録し、APPROVE利用者はINITIAL 3〜5品目またはFULL 20〜50品目をcenter・理由付きで確定する。候補計算は独立Workerが行い、画面はサーバー台帳を再読込する。詳細は[Phase1V_重要品目選定画面.md](Phase1V_重要品目選定画面.md)。

Phase 1WでFastAPIと同一originの`/ui/acceptance`を追加した。READ利用者は受入caseの処理状態、技術outcome、10項目の実測・期待値、品質レポートURI・checksum、業務判断履歴を参照できる。ANALYZE利用者はINITIAL 3〜5品目からcaseを登録し、APPROVE利用者は技術判定後に版・理由付き判断を記録する。APPROVEDはREALかつPASSEDへ限定し、Worker処理、最終認可、監査主体はサーバーが確定する。詳細は[Phase1W_実データ受入画面.md](Phase1W_実データ受入画面.md)。

Phase 1XでFastAPIと同一originの`/ui/intake`を追加した。READ利用者は取込・正規化job、原本checksum・encoding・重複/訂正系譜、原本採用履歴、数量照合、正規化行を参照できる。ANALYZE利用者は管理対象入力root内の取込job、内容アドレス方式の列mapping、正規化jobを登録し、APPROVE利用者は訂正版候補を版・理由付きで採用する。正規化行は状態条件付きのページAPIで取得し、Worker処理、最終認可、監査主体はサーバーが確定する。詳細は[Phase1X_原本取込正規化画面.md](Phase1X_原本取込正規化画面.md)。

Phase 1YでFastAPIと同一originの`/ui/matching`を追加した。READ利用者は名寄せjob、内容アドレス条件、候補根拠、center別数量、版付き判断履歴、canonical product、JAN有効期間を参照できる。ANALYZE利用者は成功済みかつ現在採用中の正規化jobから名寄せjobを登録し、APPROVE利用者はcanonical product、4種類の判断、JAN有効期間を理由・版付きで追記する。名称一致だけでは商品を統合せず、候補生成は独立Worker、最終認可と監査主体はサーバーが確定する。詳細は[Phase1Y_JAN名寄せ商品マスター画面.md](Phase1Y_JAN名寄せ商品マスター画面.md)。
