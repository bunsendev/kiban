# Portableの欠損検知と予測方式選択

pilot.53は、取り込んだ在庫・出荷データの不足を現場画面で確認し、不足を補充して通常予測するか、対応するモデルで欠損を残した暫定予測を行うか選択できる。原本・既存の正常データ・過去の結果は保持する。

## 日常の操作

1. CSV・ZIPをアップロードするか、`Data/Incoming`に置く。PDFは従来どおり読取・原本確認・正式取込用データの準備を行う。
2. 現場画面の「データの充足状況・不足一覧」で、対象期間、基準日、不足日数・レコード数、充足率を確認する。
3. 必要なら倉庫・JAN／商品名・対象日・異常区分で絞り込む。「日付別にまとめる」を外すと商品別の明細を表示する。一度に50件ずつ取得する。
4. 初期選択はA「不足を補充して通常予測」。不足一覧から追加取込へ戻り、同じ倉庫の不足分を取り込む。「追加・修正後に再検証」で確認する。異内容の同日CSVは勝手に合算・上書きしない。
5. C「欠損を残して暫定予測」は、既定の前週同曜日モデルで全14対象日を計算できる商品・倉庫だけが対象。欠損内容と影響を確認し、同意チェック・確認者・理由を入力して実行する。
6. B「推定補完して予測」は今後対応。画面では選択できず、APIから指定しても実行しない。
7. 結果画面・保存済み予測・CSVに「暫定予測」が残る。修正とフィードバックは担当者の判断として別に保存する。元の予測が通常予測に変更されるわけではない。

欠損を埋めた後の通常予測は新しい結果として保存する。過去の不足一覧には、後続の検証で補充を確認できたものを「補充済み」と表示する。後続の検証範囲から外れたものは、補充済みと決めつけず再確認を案内する。

## 予測方式の条件

| 方式 | 入力と条件 | 結果 |
|---|---|---|
| A | 通常の直近28日条件、在庫承認、JAN・倉庫・数量照合等の既存条件を維持。設定された休業日・取扱期間は別に判定 | 通常の参考予測。計算できない系列は理由を残す |
| B | 未実装 | 実行不可。Phase 2で対応 |
| C | 最小7観測に加え、各予測日の同曜日候補が必要。NaNを残し、元のデータは補完しない | 欠損を残した暫定予測 |

実際のPilot Scopeに候補モデルが割り当てられている場合、Cのために既定モデルへ切り替えない。正式予測の開始時とWorker受渡し時の両方で実モデルを確認する。観測不足、同曜日候補なし、原本の重大な不備、将来の基準日、古い検証ID等は実行を制限する。

既存のProduction Runは1つの共通予測基準日を持つ。複数倉庫で基準日が異なる場合、古い倉庫の予測を黙って新しい日へずらさず、対象外理由を残す。新たに同時予測するには、倉庫の基準日を揃える。不足で計算できない新しい倉庫だけに全体の基準日を引きずらせない。保存済みの古い倉庫の結果は引き続き参照できる。

在庫CSVがない経路の「需要予測のみ」でもCを選択できる。これは在庫・補充・欠品リスクを評価しない参考値である。通常の在庫付き結果とは区別する。

暫定予測からの在庫評価は、さらに担当者の明示確認が必要。出荷の自動確定はしない。過去日・当日・確定済み実績に対する数量変更制限は従来どおりであり、暫定方式で解除されない。

## 0と不足を区別する

- 数値0は正常。在庫ファイルの未受信、商品行の省略、未確認数量の空欄は在庫0に変換しない。
- 在庫PDF「現在欄の空欄0」の承認済み帳票ルールは従来の対象範囲内だけで適用する。
- 日次出荷ファイル内の商品行省略を0とする方針は別の設定・確認である。月次ファイルの出荷行が存在するだけでは、他日の出荷0を証明しない。
- 商品×賞味期限×ムロオ倉庫入庫日の正当な複数明細は、重複という理由で削除しない。
- 確認済み倉庫間移動の除外を維持する。新しい出庫逆算、調整の再加算、推定入庫は行わない。
- 従来の35日参考バックテストでも、未観測の正解値を0へ変換せず、精度の計算対象から分ける。

## IT担当者の設定

現場画面上部の「データ受信・欠損の設定」は現在の設定を表示する。変更は、配布フォルダーの`Feedback接続設定_管理者.cmd`からWindows管理者として開いた画面で行う。有効期限付きの既存管理者認証を使い、日常担当者に設定変更を求めない。

設定者・理由を付け、JSONを新しい版として保存する。保存後は対象の分析画面で再検証する。古い版を上書きせず、過去時点にはその時点で既知の版だけを選ぶ。

```json
{
  "warehouses": [
    {
      "warehouse": "原本と同じ倉庫名",
      "from": "2026-01-01",
      "to": null,
      "weekdays": [0, 1, 2, 3, 4, 5, 6],
      "closed_dates": [],
      "products": [{"jan": "確認した13桁JAN", "from": "2026-01-01", "to": null}],
      "master_jans": null,
      "absence_means_zero": false,
      "receipt_due_time": "23:59",
      "abnormal_change_cases": null
    }
  ]
}
```

`weekdays`は月曜0〜日曜6。`products`は個別商品の取扱期間であり、空の一覧を「全商品非取扱」とは解釈しない。`master_jans`に確定した13桁JANの一覧を設定すると、未登録のJANを別に警告する。nullの場合はマスター登録済みと保証しない。

`receipt_due_time`は日本時間。受信予定が未設定の倉庫は、既存の全暦日稼働という仮定で日付不足を表示する。予定が不明な状態を「予定ファイル未受信」と断定しない。未来日の未着や確認済み休業・取扱期間外を不要な不足として数えない。

`abnormal_change_cases`は、CASEとして正規化された在庫の前後差を確認するボール数の閾値。単位未確認の数量にボールの閾値を当てない。閾値超過は移動・調整等を確認する警告で、原本数量を自動修正しない。

## 保存先とAPI

品質履歴は`Data/State/data-quality.sqlite3`に保存する。スキーマ1の追記型レコードは受信履歴、設定版、検証版、実行参照と、検証が参照した原本の索引を持つ。原本・業務DBを作り直さない。

CSV・ZIPの受信時刻、業務対象日、最終正常取込、予測実行時刻は分離する。旧版から引き継いだファイルの実受信時刻を新たに捏造しない。PDF原本の受信時刻は`documents.sqlite3`、承認後のCSV取込は品質履歴を参照する。

主なAPIは次のとおり。

- `GET/POST /api/data-quality/rules`（変更だけ管理者認証必須）
- `GET/POST /api/business-archives/{analysis_id}/data-quality`
- `GET /api/data-quality/{check_id}/issues`（倉庫・商品・日付・区分・状態、日付集約、上限200件）
- `GET /api/business-archives/{analysis_id}/data-quality/history`
- 既存の予測開始APIに`forecast_mode`、`check_id`、`request_id`、`confirm_provisional`を追加

要求・結果には品質検証IDと方式を固定する。原本・集計・設定・判断・除外ルール・対象日が変われば別の検証版を作る。品質参照を持つmanifestは方式を含めてハッシュ照合する。元データと新DBは既存の学習データバックアップの対象である。
