# Phase 2J 初回データ検証ウィザード

## 目的

`/ui/intake`で、基盤の用語に詳しくない利用者もCSVを選び、列の対応付けを確認し、検証結果から修正箇所を判断できるようにする。元CSV、原本台帳、正規化台帳は検証操作で変更しない。

## 準備

1. `.env`の`KIBAN_IMPORT_ROOT`をCSV配置フォルダーに設定する。
2. 対象CSVをそのフォルダーまたは配下へ置く。
3. `docker compose --profile worker up -d --build api mapping-dry-run-worker`を実行する。
4. `http://127.0.0.1:58000/ui/intake`を開き、開発用tokenで接続する。

ComposeではAPIとWorkerへ同じ入力領域をread-onlyで割り当てる。ブラウザーから任意のローカルpathやCSV本文を送信しない。

## 操作手順

1. 「CSVを選ぶ」で対象を選択する。画面にサイズ、文字コード、ヘッダーが表示される。
2. 「列の対応付けを選ぶ」でCSVに合う設定を選択する。設定がなければ「新しい対応付けを作成」から登録する。
3. 不足列の案内が出た場合は、対応付けを選び直すか列名を合わせた設定を作成する。
4. 必要に応じて検査する最大行数を1〜10,000で変更し、「このCSVを検証」を押す。
5. 画面は2秒ごとに状態を更新する。成功すると検証結果へ移動する。
6. 「合格」は次工程へ進める。「要確認」は隔離理由に沿ってCSVを修正する。「処理不可」は不合格項目の修正方法を実施して再検証する。

## API契約

`GET /api/mapping-dry-run-sources`は`READ`権限を要求する。設定済み入力rootの配下にある通常の`.csv`だけを最大100件返す。symlinkとroot外pathを除外し、読み取るヘッダー量と列数に上限を設ける。応答にはデータ行、絶対path、原値を含めない。

検証jobの登録と実行契約はPhase 2Iを維持する。UIの事前確認は操作ミスを減らす案内であり、Worker側の安全性・契約検査を代替しない。

## 時刻と履歴

job時刻はPostgreSQLで`TIMESTAMPTZ`として保存し、APIはUTCオフセット付きISO 8601を返す。旧`TIMESTAMP`列はUTCとして移行する。ブラウザーは利用者のローカル時刻へ変換する。

履歴は検証job、証跡、取込job、正規化jobごとに直近20件を表示し、表示件数と該当総数を併記する。

## 受入条件

- CSV本文や絶対pathが候補APIへ出ない。
- 対応付けに必要な列が不足すると実行ボタンが無効になる。
- jobのQUEUED/RUNNINGを自動更新し、完了後に結果を表示する。
- 固定check codeを日本語の検査名と確認・修正方法へ変換する。
- tokenをWeb Storageへ保存しない。
