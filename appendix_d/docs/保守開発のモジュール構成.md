# 保守開発のモジュール構成

## 目的

機能追加のたびに1つのファイルへAPI、業務判断、保存、画面表示を積み上げない。変更理由が同じコードを同じモジュールへ置き、別の業務領域へ影響せずに追加・交換・試験できる構成を維持する。

行数は分割を検討するきっかけであり、短くすること自体を目的にしない。目安として300行を超えたファイルは責務の混在を確認し、データ契約の一覧など一体で読む価値が高い場合だけ同居を続ける。

## 依存方向

```text
UI / API route
      ↓
application service / processor
      ↓
domain / contracts
      ↓
store・providerなどの実装
```

- UIとAPI routeは入力、認可、HTTP形式への変換だけを担当する。
- 業務条件、状態遷移、集計はservice、processor、domainへ置く。
- domainはFastAPI、PostgreSQL、ブラウザーへ依存させない。
- storeはdomainの結果を保存し、判断規則を持たせない。
- Workerはjob取得とservice呼出しを担当し、HTTP request内で重い処理を実行しない。

## APIの構成

`forecast_provider/api/app.py`はcomposition rootである。認証、store、service、route installerを組み合わせるが、個別endpointの処理は置かない。

| モジュール | 責務 |
|---|---|
| `core_routes.py` | health、session、snapshot、experiment、run |
| `mapping_dry_run_routes.py` | データ受入系route installerの組み立て |
| `mapping_dry_run_report_routes.py` | 検証済み証跡の参照 |
| `mapping_dry_run_source_routes.py` | source一覧、upload、構造診断、JAN橋渡し、preview |
| `mapping_dry_run_job_routes.py` | 単一・一括ドライランjob |
| `inventory_normalization_routes.py` | 在庫正規化job、判断、特徴量view、CSV発行 |

新しいendpointは、既存モジュールと同じ変更理由ならそのinstallerへ追加する。別の台帳、権限、状態遷移を持つ場合は新しい`*_routes.py`とserviceを作り、`app.py`からinstallerを1回呼ぶ。

## 業務機能の基本形

新しい業務領域は必要な部品だけを次の形で追加する。

```text
forecast_provider/<feature>/
  contracts.py       外部へ公開する型とProtocol
  domain.py          純粋な判断・検証規則
  service.py         use caseと状態遷移
  records.py         DB rowとの変換
  store.py           SQLite実装
  postgres_store.py  PostgreSQL実装
  schema.sql         永続化schema

forecast_provider/api/
  <feature>_schemas.py
  <feature>_routes.py
```

小さな機能で不要なファイルは作らない。SQLiteとPostgreSQLで同じ業務判断を重複実装せず、共有serviceと契約を利用する。

## UIの構成

管理画面は次の責務を分離する。

| 接尾辞 | 責務 |
|---|---|
| `_api.js` | HTTP呼出しとresponse取得 |
| `_forms.js` | form値からrequestを作る純粋処理 |
| `_render.js` | DOM表示。APIを直接呼ばない |
| `_app.js` | 状態、画面遷移、各moduleの接続 |
| `_workflows.js` | 複数APIを順番に呼ぶ独立した操作フロー |

`_app.js`へ新しいHTML生成やAPI詳細を追加しない。画面内に独立した操作フローが増える場合は`_<capability>_workflows.js`へ分け、必要なcallbackだけをappから渡す。

## Providerの構成

予測モデル追加時は、既存のTimesFM、MLForecast、StatsForecastと同じ境界を使う。

- provider本体: 契約の検証、fit、predictの調整
- codec: JSON artifactのencode・decode
- state/runtime: OSS固有modelの生成と実行
- executor: 共通run処理との接続
- worker entrypoint: Provider IDでqueueを分離

checkpoint download、pickle復元、任意module実行をAPIから受け付けない。新しいProviderが既存Providerの条件分岐として増え始めた場合は、registryと個別executorへ分ける。

## 追加開発時の確認

1. 変更理由を1文で説明し、その責務を持つmoduleを決める。
2. HTTP schema、業務契約、保存形式を同じclassへ混在させない。
3. 既存の巨大ファイルへ追記する前に、独立installer・service・rendererで接続できないか確認する。
4. public URL、response、DB schemaを変えずに分割できる場合は、先に構造だけを整理する。
5. 対象領域のtestを実行し、その後に全pytest、ruff、release照合を行う。

## 次に分割を検討する箇所

優先順位は、行数だけでなく変更頻度と責務数で決める。

1. `ui/static/intake_app.js`: upload、検証、在庫、mappingのworkflowを段階的に分離する。
2. `providers/builtin_baseline.py`: 区間予測とartifact組立ての変更が増えた場合に分離する。
3. `jobs/sqlite_store.py`: query群をrecords変換と永続化操作へ分ける。
4. `contracts.py`: 契約の参照性を保ちつつ、領域別importへ移行できる時点で分割する。

これらは動作変更と同時に一括分割しない。既存の回帰試験が通る小さな構造変更として順番に実施する。
