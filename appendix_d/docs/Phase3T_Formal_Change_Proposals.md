# Phase 3T 正式変更案と別承認

## 目的

手順13で`RECOMMEND_FORMAL_CHANGE`となった比較runを、実装可能な変更案へ変換する。比較結果の判断と設定変更の承認を分離し、変更差分、適用範囲、受入基準、rollback条件を先に固定する。

## 操作

1. 手順13でBaselineとChallengerを比較し、「正式変更案の作成を推奨」を記録する。
2. 手順14で対象runと変更種別を選ぶ。
3. 現行設定、変更後設定、適用範囲をJSONで入力する。
4. 受入基準とrollback条件を1行1件で入力し、rollback先版を指定する。
5. 内容を固定後、案の作成者とは別の担当者が承認または却下する。

## 変更対象

需要予測の比較からは、需要予測モデル、需要予測の入力項目、データ契約を提案できる。推奨出荷量の比較からは、推奨出荷Policy、配送Route Policy、データ契約を提案できる。異なる用途の組み合わせは拒否する。

## 監査契約

- 元の比較run IDと`RECOMMEND_FORMAL_CHANGE`のrevisionを固定する。
- 提案は内容ハッシュを持ち、同じIDの内容変更を拒否する。
- 判断は期待revisionを使う追記型eventとし、競合を拒否する。
- 元の比較判断が更新・撤回された場合、古い提案の承認を拒否する。
- 提案者と承認者を同一にできない。
- 現行設定と変更後設定が同じ提案、空の適用範囲、受入基準、rollback条件を拒否する。

## 適用境界

`APPROVED_FOR_IMPLEMENTATION`は、実装・受入試験を行う次工程へ進める判断である。モデル、特徴量、route、安全在庫、出荷単位、現場設定を更新しない。画面とAPIは常に`application_status=NOT_APPLIED`を返す。

実際の適用では、別の変更版、限定したPilot Scope、受入結果、適用時刻、適用者、rollback実行契約が必要になる。承認済み提案だけで現場環境を変更してはならない。
